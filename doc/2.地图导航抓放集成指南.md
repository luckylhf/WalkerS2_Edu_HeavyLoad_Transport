# 地图导航抓放集成指南

本文面向 Walker S2 真机，将已有地图导航与本项目的点云检测、双臂 IK、HTTP
关节动作串成一次“到取箱点—抓取—经中间点搬运—到放置点—放置”的单程流程。首次测试必须使用
`--debug`，并由一名操作员和一名安全监护员共同执行。

> **开机前置**：运行本文任何建图、导航或抓放步骤前，必须先按
> [机器人开机与任务前置检查](./1.机器人开机与任务前置检查.md)完成上电前环境检查，并严格
> 执行遥控器 **D 回零 → A 站立**，确认机器人稳定站立。程序中的 `SetLegMode STAND`
> 不能替代该人工前置；任一检查失败时禁止执行任务。

## 1. 固定名称、边界与资料来源

本项目默认值区分大小写，建图、打点和运行参数必须完全一致：

| 项目 | 本项目固定值 | 用途 |
| --- | --- | --- |
| 地图 ID | `lqx3` | `SetMap` 的 `mapId` |
| 取箱点 | `box1` | 第一次 `NavTo` 的 `targetId` |
| 搬运中间点 | `mid1` | 第二次 `NavTo` 的 `targetId` |
| 放置点 | `put1` | 第三次 `NavTo` 的 `targetId` |

原始 [AB 点全流程导航 SOP](./AB点全流程导航SOP/AB点全流程导航SOP.md)
中的 `yungu_wrc`、`Box1`、`Put1` 是原流程示例，不是本项目参数；原 SOP 的遥控器
启动组合键和最多 50 次循环也不适用于本程序。本程序通过 `ubt_robot` SDK 启动技能，
只执行一轮，任一步失败即中止。

内容来源如下：

- 标定、场景、建图注意事项、二维码距离和 UMAP 说明来自
  [AB 点全流程导航 SOP](./AB点全流程导航SOP/AB点全流程导航SOP.md)。
- Web 建图、精确打点、保存地图、定位和单点导航操作来自
  [Web 导航系统 SOP](./web导航系统sop/web导航系统sop.md)。
- SDK 打包和系统依赖见
  [`vendor/ubt_robot/README.md`](../src/box_grasp_demo/vendor/ubt_robot/README.md)。

## 2. 建图与地图点位准备

### 2.1 现场和机器人准备

1. 完成标零、双目标定、四目标定，启动运控；已有合格地图时可以导入后跳过重建。
2. 清空建图和导航通道，避免人员、线缆、活动桌椅进入路线；保留现场认可的硬停或急停手段。
3. 原 AB 点 SOP 的参考场景为两张约 80 cm 高、呈 90°、间距至少 65 cm 的桌子，
   A/B 点按顺时针布置，箱体/二维码按原 SOP 放置，且应避开大面积白墙等无特征区域。
4. 本项目当前配置不是原 SOP 的 80 cm 参数：抓取桌 `table_height: 0.85` m，放置桌
   `place_table_height: 0.88` m。真机桌高必须与
   [`box_grasp_ros2.yaml`](../src/box_grasp_demo/config/box_grasp_ros2.yaml)
   一致；若现场尺寸不同，应先由感知/IK 负责人重新标定配置，不能只沿用原 SOP 场景数值。

若需要保留导航诊断数据，原 AB 点 SOP 还说明了在 Udoke 中启用
`freepnc.record_enable` 的方法；每次流程的 bag 位于机器人
`/etc/walker/log/nav/`。入口和账号信息请直接查原 SOP，不在本文重复。

### 2.2 创建并保存 `lqx3`

1. 打开 Web 导航系统，选择“创建地图”。
2. 选择“开始建图”，地图名称严格填写 `lqx3`，保存后开始移动机器人建图。
3. 覆盖 `box1`、`mid1`、`put1`、三点之间的完整路线和必要回转空间；经过墙角、桌腿等稳定特征，
   不要只贴着白墙行走。
4. 完成后点击“结束建图”保存结果；左上角“退出”会取消建图并删除本次地图，不能当作保存。

关键界面链接：
[创建地图](./web导航系统sop/图片和附件/image%2013.png)、
[开始建图](./web导航系统sop/图片和附件/image%2017.png)、
[结束并保存](./web导航系统sop/图片和附件/image%204.png)。完整图示以 Web SOP 为准。

### 2.3 精确打 `box1`、`mid1` 和 `put1`

优先使用 Web“编辑地图 → 精确打点”，因为它保存机器人当前真实位姿和朝向：

1. 编辑 `lqx3`。此操作会先把它设为当前地图并重定位；等待定位成功后再打点。
2. 将机器人移动到取箱工作位。按原 AB 点 SOP，打点时机器人脚尖距二维码约 60 cm；
   同时确认相机能完整看到箱体、双臂有展开空间。
3. 进入“精确打点”，点击“插入点位”，名称严格填写小写 `box1`。
4. 在从取箱点到放置点的安全搬运路线上选择一个中间过渡位置，插入小写 `mid1`；该点应有
   足够转身和负载通过空间，不能贴近桌边、墙角或人员通道。
5. 将机器人移动到放置工作位，以同样方法插入小写 `put1`；朝向应让箱体放置目标落在
   当前 IK 可达区域。
6. 如现场使用二维码精定位，按 Web SOP 配置二维码点定位。打点后 UMAP 会同时包含
   自由导航目标点和相应二维码精定位信息。
7. 点击“保存地图”覆盖当前 `lqx3`；不要误选“另存为”生成另一个地图 ID。

关键界面链接：
[精确打点](./web导航系统sop/图片和附件/image.png)、
[插入点位](./web导航系统sop/图片和附件/image%202.png)、
[二维码点定位设置](./web导航系统sop/图片和附件/image%2029.png)。

### 2.4 在接入抓放前单独验收导航

在 Web 导航页先设置 `lqx3` 并重定位。优先使用自动定位（全局重定位）；局部/强制定位
仅适用于 Web SOP 标明支持的机型。分别只添加 `box1`、`mid1`、`put1` 并各导航一次，检查：

- 三个 ID 都能被选中且导航成功；
- 到点后的脚尖—二维码距离和机身朝向适合抓放；
- 路线、转身半径和桌边间隙安全；
- 重启或重新设置地图后仍能全局重定位。

定位和导航界面见
[定位页](./web导航系统sop/图片和附件/image%2010.png) 与
[添加目标并导航](./web导航系统sop/图片和附件/image%2020.png)。三点未分别通过前，
不要运行集成工作流。

## 3. SDK、Python 3.10 与构建

`ubt_robot` 是 CPython 3.10 二进制 SDK。本项目随包提供
`linux_x86_64` 和 `linux_aarch64` 两份 wheel；`colcon build` 的安装阶段会按
`platform.machine()` 选择唯一匹配项，直接解包到当前 ROS install prefix 的
`lib/python3.10/site-packages`。它不访问网络、不调用 `pip`，也不写系统 Python。

wheel 仍依赖系统的 `libmosquitto.so.1`（Ubuntu 包名 `libmosquitto1`）。在真机工作区
（项目约定为 `/home/ubt/demo3`）执行：

```bash
cd /home/ubt/demo3
source /opt/ros/humble/setup.bash
conda deactivate 2>/dev/null || true

/usr/bin/python3.10 --version
sudo apt update
sudo apt install -y libmosquitto1

colcon build --packages-up-to box_grasp_demo --symlink-install \
  --cmake-args -DPYTHON_EXECUTABLE=/usr/bin/python3 \
               -DPython3_EXECUTABLE=/usr/bin/python3
source install/setup.bash
```

构建要求 `/usr/bin/python3.10` 为 CPython 3.10；激活的 conda 不能替代 SDK 的 ABI。
CMake 会固定该解释器；`navigate_box_workflow.py` 本身也显式使用
`/usr/bin/python3.10`。
构建后验证：

```bash
/usr/bin/python3.10 -c "import ubt_robot; print(ubt_robot.__file__)"
ldconfig -p | grep libmosquitto.so.1
```

若 SDK 导入失败，不要对 wheel 执行手工 `pip install`；先按第 9 节排查架构、Python、
install 环境和共享库。

## 4. 启动检测与 IK，并做运行前检查

终端 A 启动感知和 IK。项目真机脚本会重新构建、激活 conda `ik` 环境、生成或复用
`.casadi_cache/ik_solver.so`，最终以 `/demo3` 命名空间启动检测和 IK，且不直接驱动手臂：

```bash
cd /home/ubt/demo3
./run.sh
```

仓库中的对应脚本是 [`tools/robot_run.sh`](../tools/robot_run.sh)。保持终端 A 运行，
另开终端检查：

```bash
cd /home/ubt/demo3
source /opt/ros/humble/setup.bash
source install/setup.bash

ros2 topic type /sensor/camera/stereo/pointcloud/raw
ros2 topic echo /mc/joint_states --once
ros2 action info /demo3/box_grasp_demo/detect_box
ros2 service type /demo3/box_grasp_demo/suggest_crouch
curl_args=(-fsS)
if [[ -n "${MOTION_PROXY_API_KEY:-}" ]]; then
  curl_args+=(-H "X-API-Key: ${MOTION_PROXY_API_KEY}")
fi
curl "${curl_args[@]}" http://192.168.11.2:12300/healthz
```

期望点云类型为 `sensor_msgs/msg/PointCloud2`，`/mc/joint_states` 能返回，DetectBox
action server 和 `suggest_crouch` service 存在，终端 A 出现“IK 求解器就绪”，HTTP
健康检查返回成功。HTTP 服务由现场代理部署提供，本程序不会启动它；完整部署、鉴权限制、
日志和安全说明见 [HTTP 运动代理启动指南](./3.HTTP运动代理启动指南.md)。若 UDoKe 尚未管理
该模块，最小前台启动摘要是在 Walker `motion` 容器中执行：

```bash
cd /proxy_server
bash run_motion_http_proxy.sh
```

默认地址为 `http://192.168.11.2:12300`；若地址不同，运行工作流前设置
`MOTION_BASE_URL=http://<host>:<port>`。代理启动和 healthz 成功均不代表机器人动作安全。

## 5. 运行命令

终端 B 先加载 ROS 和本工作区。自动模式没有日常确认，仅允许在完整 debug 验收后使用：

```bash
cd /home/ubt/demo3
source /opt/ros/humble/setup.bash
source install/setup.bash

ros2 run box_grasp_demo navigate_box_workflow.py \
  --map-id lqx3 --pick-target box1 --mid-target mid1 --place-target put1
```

首次真机必须使用 debug，并显式写出地图和三个点位参数便于复核：

```bash
ros2 run box_grasp_demo navigate_box_workflow.py \
  --map-id lqx3 --pick-target box1 --mid-target mid1 --place-target put1 --debug
```

SDK 默认连接地址来自当前代码的 `0.0.0.0:51000`，连接超时默认 10 秒。若现场要求指定
机器人地址：

```bash
ros2 run box_grasp_demo navigate_box_workflow.py \
  --map-id lqx3 --pick-target box1 --mid-target mid1 --place-target put1 \
  --address 192.168.11.2 --connect-timeout 10 --debug
```

`--address` 只写主机时，程序自动补 `:51000`。若 launch 改了命名空间，还必须用
`--action-name` 指向对应 DetectBox action；可先用 `--help` 查看当前全部参数。

## 6. 本项目 18 步 debug 状态机与确认

在 debug 模式中，每个高层步骤开始前都会显示
`[DEBUG] 高层步骤“...”将改变机器人状态，是否执行？[y/N]`。只有 `y` 或 `yes`
会继续；直接回车、其他输入或 EOF 都会取消当前步骤，并中止余下流程。

| # | 高层步骤 | 实际操作 | 输入 `y` 前确认 |
| ---: | --- | --- | --- |
| 1 | 激活 biped home（流程开始，仅一次） | HTTP `s2/move_biped_home`，等待站立高度 | 机器人支撑稳定，站立空间和头顶空间无障碍。 |
| 2 | SetMap `lqx3` | `A000012 {mapId: lqx3}` | 屏幕参数确为 `lqx3`，现场与该地图一致。 |
| 3 | Relocation global | `A000013 {mode: global}` | 人员退出运动区；等待全局定位明确成功。 |
| 4 | NavTo `box1` | `A000002 {targetId: box1}` | 路线清空，遥控器/急停在手；到点后核对距离、朝向。 |
| 5 | 腰部后仰（抓取前） | `waist` 组件 `pitch=+0.32 rad`（约 +18.3°） | 腰部后仰方向正确，脚底稳定，头部和箱体区域无干涉。 |
| 6 | 准备拍照姿态 | 必要时经 HTTP 发送手臂/头部轨迹并等待到位 | 双臂、头部全程无碰撞；若已在拍照位会直接跳过动作。 |
| 7 | 拍照前下蹲 | 请求 `photo` 下蹲量，直接发送绝对下蹲量并等待高度（biped home 已在步骤 1 激活一次） | 双脚稳定、桌面与机身无干涉，建议高度合理。 |
| 8 | 检测箱子 | 发送 DetectBox goal，要求 `success=True` 且 `ik_data` 非空 | 点云无遮挡；结果中的中心、尺寸、下蹲量和 5 组 IK 合理。 |
| 9 | 抓取前下蹲 | 请求 `grasp` 下蹲量，直接发送绝对下蹲量并等待（无需再次 home） | 箱体未移动，手臂目标仍可达，机身不会撞桌。 |
| 10 | 执行抓取段 | HTTP 依次发送预抓取、抓取、抬起、收回 4 组 14 关节目标 | 每个内部路点还会单独询问；收回后箱体中心姿态应为 `rx=ry=rz=0`。 |
| 11 | 恢复导航高度（抓取后） | HTTP `/v1/motions` 发送 biped 绝对下蹲量 `0.0`，等待站立高度；不再调用 home | 箱体夹持稳定、手臂不碰桌，升高后重心可控。 |
| 12 | NavTo `mid1` | `A000002 {targetId: mid1}` | 负载和路线安全；确认中间点有足够转身/通过空间。 |
| 13 | NavTo `put1` | `A000002 {targetId: put1}` | 负载和路线安全；监护员跟随但不进入机器人路径。 |
| 14 | 放置前下蹲 | 请求 `place` 下蹲量，直接发送绝对下蹲量并等待（无需再次 home） | 放置台空闲、位置/高度正确，箱体不会撞台边。 |
| 15 | 重算并执行当前放置段 | 调用 `compute_place_ik` 按 put1 的当前高度/TF 重算 14 关节解，再经 HTTP 放置并返回拍照位置 | 不复用抓取时的 place 缓存；两个内部路点分别确认，先确认箱体已受台面支撑。 |
| 16 | 恢复导航高度（放置后） | HTTP `/v1/motions` 发送 biped 绝对下蹲量 `0.0`，等待站立高度；不再调用 home | 箱体已稳定放下、双臂与桌面分离且回升空间安全。 |
| 17 | 腰部恢复（放置后） | `waist` 组件 `pitch=0` | 箱体已由台面支撑，回正不会碰桌或改变箱体状态。 |
| 18 | 收起双臂 | HTTP 发送拍照位到双臂零位轨迹并等待到位 | 双臂收回路径无人员、桌面或其他障碍。 |

还要理解第二层确认的语义：

- 步骤 5、6、10、11、14、15、16、17、18 的必要 HTTP 动作会再次确认；拒绝会返回失败并中止。
- 步骤 7、9、14 若建议下蹲量接近 0 会直接跳过动作；除此以外，用户拒绝下蹲会使
  当前步骤失败并中止全流程。
- 整轮流程只在步骤 1 调用一次 `s2/move_biped_home`。步骤 11、16 的站直
  与其他下蹲调整一样，都通过 `/v1/motions` 发送 biped 绝对下蹲量。
- 等待拍照位、下蹲高度、导航高度或手臂路点超时均严格失败，不提供带风险继续选项。
- debug 下读不到 `/mc/joint_states`、取不到下蹲建议或重算 place IK 失败也都会中止，
  不会把缺失的安全前置条件当作成功。
- HTTP 返回 200 只代表命令被接收。程序随后通过 `/mc/joint_states` 或 TF 等待真实到位；
  没有“到位”日志就不能确认下一步。

## 7. 中止、失败策略与安全边界

### 7.1 Ctrl+C 和失败即中止

- 任一高层 action 返回 `False`、抛出异常、debug 拒绝确认，都会标记当前步骤失败或取消，
  后续步骤保持 `PENDING`，流程立即中止并打印 18 步摘要。
- 当 `SetLegMode`、`SetMap`、`Relocation` 或 `NavTo` 的 UBT Work 正在执行时，
  `Ctrl+C`/SIGTERM 会立即调用当前 `work.stop()`，然后停止 API、销毁 ROS node 并退出。
- 没有 UBT Work 在途时，信号会中止本地编排；SIGINT 通常退出码为 130，SIGTERM 为 143。
  SDK/ROS 依赖加载失败退出码为 3，普通步骤失败为 1，完整成功为 0。
- 本项目现场约定遥控器 **D 键用于回零、A 键用于切换站立**，不能把 A 键当作本流程的
  停止键。首次测试应让熟悉运控的人员持遥控器，并以现场另行验证的急停/硬停方式为
  最终安全手段，不能只依赖终端 Ctrl+C。

### 7.2 当前实现不能保证的事项

- **已被 HTTP 服务接收的机械臂或 biped 动作不能由本程序撤回。** 当前代码没有 HTTP
  cancel/stop 请求；命令发出后再按 Ctrl+C 只会终止本地流程或在途 UBT Work，机器人
  端已接受的 HTTP 动作可能继续。此时应使用现场验证过的机器人停止手段。
- 导航工作流退出清理会调用 `cancel_goal_async()` 尝试取消活动中的 DetectBox goal；
  取消请求失败或超时仍按清理错误处理。它只针对感知/IK action，不会停止机器人已经接收的
  HTTP 机械臂、biped 动作，也不能替代现场停止手段。
- HTTP 关节目标是直接发送的，不经过 MoveIt 路径规划或碰撞检测；程序只比较最终关节
  误差。监护员必须检查整个运动包络，而非只看目标姿态。
- 当前流程没有力传感器接触判定、夹持力/载荷稳定性闭环，也不会因箱体滑移自动急停。
- 工作流只执行 `lqx3: box1 → mid1 → put1` 一次，没有原 SOP 的反向搬运和循环功能。

## 9. 故障排查

| 现象 | 检查与处理 |
| --- | --- |
| 构建报 CPython 不兼容 | 执行 `/usr/bin/python3.10 --version`；退出 conda，清楚地区分系统 Python 与 conda `ik`。wheel 只支持 CPython 3.10。 |
| wheel 不匹配或找不到 | `uname -m` 只能是 `x86_64/amd64` 或 `aarch64/arm64`；确认 vendor 目录内对应 wheel 唯一存在，重新 `colcon build`，不要手工 pip 安装。 |
| `import ubt_robot` 失败 | 先 `source install/setup.bash`；确认安装前缀的 `lib/python3.10/site-packages` 已进入 `PYTHONPATH`。若报 `.so` 加载错误，用 `ldd` 检查 `_core*.so` 的 `not found`。 |
| 缺少 `libmosquitto.so.1` | `sudo apt install -y libmosquitto1`，再用 `ldconfig -p \| grep libmosquitto.so.1` 验证。CMake 当前只警告，运行时导入才可能失败。 |
| `连接机器人超时（10 s）` | 检查 51000 端口和网络；按现场地址传 `--address <IP>`。主机名无冒号时程序会补 `:51000`。 |
| `SetMap` 失败 | 核对地图已保存/导入，ID 严格为 `lqx3`；不要使用原 SOP 的 `yungu_wrc`。 |
| 全局重定位失败 | 回到 Web 单独定位；确认现场未大幅变化、地图特征足够，避开白墙等退化区域。不要直接强制进入 NavTo。 |
| `NavTo box1/mid1/put1` 失败或停位不对 | 核对小写 targetId、点位方向和 UMAP 保存结果；在 Web 中单点复测，必要时重新精确打点。 |
| action server 等待 5 秒后未就绪 | 保持 `run.sh` 终端运行；执行 `ros2 action info /demo3/box_grasp_demo/detect_box`，并核对 `--action-name` 与 launch 的 `ns`。 |
| 检测超时、`success` 非 True 或 `ik_data` 为空 | 检查点云/TF、箱体尺寸、桌高、工作空间和终端 A 日志；IK 必须返回完整 5×14 数据，不能复用上一次结果。 |
| `suggest_crouch service 未就绪` | 检查 `/demo3/box_grasp_demo/suggest_crouch` 和 action namespace；该错误会严格中止。 |
| `compute_place_ik service 未就绪/失败` | 检查 `/demo3/arm_ik/compute_place_ik`、左右 place target 和当前 TF；禁止退回抓取时缓存的第 5 组 IK。 |
| HTTP 健康检查失败 | `curl` 测试当前 `MOTION_BASE_URL`；确认现场 HTTP 服务/代理已启动、地址和 API key 正确。代码默认 `http://192.168.11.2:12300`。 |
| HTTP 200 后动作没完成 | 200 只表示接收。检查 `/mc/joint_states`、目标关节差、TF 和机器人告警；不要在超时提示中继续，也不要重复发送同一动作。 |
| Ctrl+C 后机器人仍运动 | 判断是否为已接收的 HTTP 动作；本程序无法撤回它。立即使用现场已验证的停止手段，并在复位前隔离运动区。 |
