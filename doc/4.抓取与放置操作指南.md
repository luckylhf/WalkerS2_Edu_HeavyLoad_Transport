# 抓取与放置操作指南

本文面向 Walker S2 真机操作员，说明当前代码下的箱体检测、抓取、搬运后放置和失败恢复。
首次真机只能使用空箱或最低风险载荷，在操作员之外安排一名安全监护员，并使用
`--debug` 逐步验收。地图创建、二维码打点和重定位界面不在本文重复，请直接阅读
[地图导航抓放集成指南](./2.地图导航抓放集成指南.md)。

> **开机前置**：运行任何检测、下蹲、抓取或放置步骤前，必须先按
> [机器人开机与任务前置检查](./1.机器人开机与任务前置检查.md)完成上电前环境检查，并严格
> 执行遥控器 **D 回零 → A 站立**，确认机器人稳定站立。程序中的 `SetLegMode STAND`
> 不能替代该人工前置；任一检查失败时禁止执行任务。

> **安全边界**：当前程序把关节目标直接交给 HTTP 动作服务，不提供力控、接触检测、
> 夹持力/载荷闭环、箱体防滑闭环、运动路径碰撞规划或自动急停。IK 收敛和终点关节到位
> 不能证明中间轨迹无碰撞，也不能证明箱子已经夹稳或已受台面支撑。全过程必须清空运动
> 包络，监护员持有现场已经验证的硬停/急停手段。

## 1. 两种流程及代码关系

当前有两个操作入口：

| 入口 | 用途 | 当前行为 |
| --- | --- | --- |
| `trigger_detect_box.py` | 不含地图导航的抓放调试入口 | 准备拍照位、执行 `photo` 下蹲、检测，然后按 DetectBox 的 5×14 数据执行预抓取、抓取、抬起、收回和原始 place，最后回拍照位；内部动作固定逐步确认。它不导航到 `put1`，也不自动执行独立的 `grasp/place` 下蹲或腰部后仰。 |
| `navigate_box_workflow.py` | 真机 `box1 → mid1 → put1` 集成流程 | 负责站立、地图、重定位和三段导航，但不另写抓放控制；它导入并复用 `trigger_detect_box.py` 的 `DetectBoxClient`，调用其中的拍照、下蹲、检测、HTTP 路点等待、腰部姿态、抓取、当前 place IK 和放置逻辑。 |

两者的关键关系是：导航程序只负责编排，实际 DetectBox action、SuggestCrouch service、
HTTP 动作以及 `/mc/joint_states`/TF 到位判断都复用 `DetectBoxClient`。因此不要把两套流程
理解成两份独立抓取实现。

`trigger_detect_box.py` 的独立入口仍是同工位调试行为：它会使用检测时返回的第 5 组
place IK，不能代替“先导航到 `put1`，再按当前高度重算 place IK”的正式搬运流程。
两桌搬运和自动模式验收应使用导航集成入口。

## 2. 抓取前准备

### 2.1 人员、现场和机器人

- 至少一名操作员和一名安全监护员；非测试人员退出导航路线和双臂、头部、箱体的完整
  运动包络。
- 标零、双目/四目标定、运控、遥控器和现场硬停/急停均已单独验证。不要把终端
  `Ctrl+C` 当作硬停。
- 首轮使用空箱，确认桌子固定、桌边无突出物、地面平整、线缆不会进入腿部或双臂运动区。
- 若使用导航流程，`lqx3`、小写 `box1`、小写 `mid1`、小写 `put1` 必须已分别单点导航成功；建图和打点
  按[地图导航抓放集成指南](./2.地图导航抓放集成指南.md)执行。

### 2.2 当前桌高和箱型

当前配置文件为
[`box_grasp_ros2.yaml`](../src/box_grasp_demo/config/box_grasp_ros2.yaml)，操作前逐项核对：

| 项目 | 当前配置 | 操作要求 |
| --- | ---: | --- |
| 抓取桌离地高度 `table_height` | `0.85 m` | 现场不一致时停止，由感知/IK 负责人重新标定，不要只改下蹲量。 |
| 放置桌系统高度 `place_table_height` | `0.78 m` | 这是 TF 与视觉口径下的系统实测值，不一定等于卷尺读数。具体可以读 [`box_grasp_ros2.yaml`](../src/box_grasp_demo/config/box_grasp_ros2.yaml)  |
| 放置离桌间隙 `place_clearance` | `0.005 m` | 仅为目标高度余量，不是接触或防压桌保证。 |
| 合法桌高范围 | `0.75–1.10 m` | 抓取桌或放置桌超范围时 DetectBox 会拒绝执行。 |
| 当前箱型 `box_model` | `small_box3` | 配置尺寸约为长 `0.40 m`、宽 `0.30 m`、高 `0.23 m`。 |
| 放置平面位置 | `x=0.40 m, y=0, yaw=-90°` | 均为 `base_link` 系；`placement_roi_enabled` 当前为 `false`，程序不会视觉识别 `put1` 台面。 |

箱体型号、装载方式、外形或桌高改变后，旧的 debug 验收作废。当前放置目标由配置和动态 TF
计算，并不代表相机确认了放置台的真实边缘、占用情况或障碍物。

### 2.3 点云与 TF

当前点云话题是 `/sensor/camera/stereo/pointcloud/raw`，目标坐标系是 `base_link`。正常真机
必须存在从点云消息 `header.frame_id`（通常为 `stereo_left_rectified_optical_frame`）到
`base_link` 的完整 TF；`camera_extrinsic_file` 当前为空，没有手眼文件回退。还必须有
`base_footprint → base_link`，因为下蹲建议、桌面过滤和放置高度都依赖它的动态 Z。

启动后检查：

```bash
ros2 topic type /sensor/camera/stereo/pointcloud/raw
ros2 topic echo /sensor/camera/stereo/pointcloud/raw --once --field header
ros2 run tf2_ros tf2_echo base_link stereo_left_rectified_optical_frame
ros2 run tf2_ros tf2_echo base_footprint base_link
ros2 topic echo /mc/joint_states --once
```

期望点云类型为 `sensor_msgs/msg/PointCloud2`，时间戳持续更新；两个 TF 可连续查询，
`base_footprint → base_link` 的 `Translation.Z` 会随站立/下蹲改变；`/mc/joint_states` 必须
包含左右臂各 7 个、共 14 个所需关节。TF 缺失、时间戳异常或关节不全时不得继续。

### 2.4 Action、Service、IK 和 HTTP

以默认 `/demo3` 命名空间启动时，接口必须同时存在：

```bash
ros2 action info /demo3/box_grasp_demo/detect_box
ros2 service type /demo3/box_grasp_demo/suggest_crouch
ros2 service type /demo3/arm_ik/compute_place_ik
curl_args=(-fsS)
if [[ -n "${MOTION_PROXY_API_KEY:-}" ]]; then
  curl_args+=(-H "X-API-Key: ${MOTION_PROXY_API_KEY}")
fi
curl "${curl_args[@]}" http://192.168.11.2:12300/healthz
```

期望 service 类型分别为 `box_grasp_demo_msgs/srv/SuggestCrouch` 和
`box_grasp_demo_msgs/srv/ComputePlaceIK`。启动终端还应出现“IK 求解器就绪”，且没有
`IK 不可到达`、TF 查询失败或持续点云异常。

HTTP 默认地址是 `http://192.168.11.2:12300`。现场地址或鉴权不同时，在启动操作入口的
同一终端先设置：

代理的构建、UDoKe/前台启动、API key 兼容性、日志和停止边界见
[HTTP 运动代理启动指南](./3.HTTP运动代理启动指南.md)。

```bash
export MOTION_BASE_URL=http://192.168.11.2:12300
export MOTION_PROXY_API_KEY='replace-with-site-key'
```

第一行请替换为现场 HTTP 地址；没有启用 API key 时不要设置第二行。不要把真实密钥写入
文档、命令历史或日志。手臂命令默认 `mode=1`、`vel_scale=0.2`；
biped 下蹲固定使用 `mode=1`、`vel_scale=0.1`。未经重新验收不要提高速度。

### 2.5 搬运腰部后仰角

导航集成流程在到达 `box1` 后、准备拍照之前发送一次 `waist` 组件命令，腰部俯仰目标默认为
`+0.32 rad`，约 `+18.3°`；代码约定正值表示后仰。该姿态会贯穿拍照、检测、抓取、收回以及
`box1 → mid1 → put1` 的负载导航，放置完成并恢复导航高度后再发送 `pitch=0` 回正，随后收起
双臂。HTTP 请求格式为 `component_names=["waist"]`、`goals=[[0.0, pitch]]`，`mode=1`、
`vel_scale=0.1`。

如现场完成了新的重心和稳定性验收，可在启动工作流前临时覆盖：

```bash
export WAIST_TILT_BACK_RAD=0.32
```

该值是弧度，不是角度；不要把 `18.3` 直接填入环境变量。改变后仰角会改变机器人重心、相机
视角和 IK 的腰部补偿，必须重新执行空箱 `--debug` 验收。当前程序只确认 HTTP 命令已接收并
等待固定收尾时间，没有订阅腰部关节做闭环到位判断，因此腰部未到目标、过度后仰或站立不稳
时必须立即中止。

## 3. 下蹲模式和绝对量语义

`/demo3/box_grasp_demo/suggest_crouch` 接受三种 `mode`：

| mode | 使用时机 | 当前高度基准 |
| --- | --- | --- |
| `photo` | 拍照/检测前 | 抓取桌 `table_height` |
| `grasp` | 执行预抓取、抓取、抬起前 | 抓取桌 `table_height` |
| `place` | 到达 `put1`、计算当前 place IK 前 | 放置桌 `place_table_height` |

返回值包括当前 `base_link` 离地高度、目标高度、站立高度，以及 `crouch_height`。其中
`crouch_height` 是**相对 biped home 站立位的绝对下蹲量**，负值向下，不是“在当前高度
基础上再下降多少”。当前配置下可预期 `photo/grasp` 约为 `-0.101 m`、`place` 约为
`-0.071 m`；这只是核对量，实际必须以当次 service 响应和 TF 为准。

每次非零下蹲都严格执行：

1. HTTP health 检查；
2. 调用 `/v1/call_action` 激活 `s2/move_biped_home`；
3. 等待 TF 到达站立 `base_link` 高度；
4. 向 `/v1/motions` 发送绝对下蹲量；
5. 等待 TF 到达目标高度。

因此即使机器人已经蹲下，再进入 `grasp` 或 `place` 也会先回 home，再按绝对值下蹲。
建议值绝对值小于 `0.005 m` 时才直接视为无需调整。当前客户端遇到 home/下蹲到位超时会
直接返回失败并中止，不能用肉眼“差不多”代替 TF 到位，也不要手工跳到下一步。

## 4. DetectBox 结果和 5×14 IK

DetectBox goal 没有请求字段，发送即开始检测。默认要求连续稳定 `4` 次，中心移动不超过
`0.02 m`；连续漏检 `3` 次会清零稳定计数。首次从未检测到箱子达到 `5 s` 会中止，稳定后
等待 IK 最长 `15 s`；客户端等待完整 action result 最长 `90 s`。
配置文件为：box_grasp_ros2.yaml

反馈字段用于观察检测过程：`stable_count` 是当前稳定计数，`miss_count` 是连续漏检数，
`box_center` 是当前帧中心，未检测时为 `[0,0,0]`，`message` 是过程说明。

结果字段含义如下：

| 字段 | 含义和验收方法 |
| --- | --- |
| `success` | 只有 `True` 才表示检测稳定完成；仍不等于机械臂动作安全。 |
| `message` | 最终人类可读说明；检查是否带“未收到 IK 关节数据”等异常后缀。 |
| `box_center` | `base_link` 系箱体中心 `[x,y,z]`，单位 m；应与现场左右、前后和桌高一致。 |
| `box_dimensions` | 箱体 `[length,width,height]`，单位 m；当前应接近 `[0.39,0.30,0.12]`，明显偏差应中止。 |
| `ik_data` | JSON 字符串，必须能解析为 5 组、每组 14 个有限数，单位 rad。空字符串或 `{"error": ...}` 均不可执行。 |
| `grasp_crouch` | 抓取阶段建议的绝对下蹲量，负值向下；集成流程仍会在抓取前通过 service 重新请求。 |
| `place_crouch` | 放置阶段建议的绝对下蹲量，负值向下；集成流程到 `put1` 后仍会重新请求 `place`。 |

终端额外打印的 `status` 是 action 协议状态，不是 `DetectBox.action` 自身的 result 字段；
必须为 `STATUS_SUCCEEDED`，并且 `success=True`。

`ik_data` 的 5 组顺序固定为：

1. `pregrasp`：预抓取；
2. `grasp`：双手到箱体侧面抓取目标；
3. `aftergrasp`：在抓取位基础上抬起；
4. `retract`：抬起后把箱子向身体收回（近身面离躯干前表面 5cm），并将箱体中心姿态目标设为 `rx=ry=rz=0`；
5. `place`：检测时刻按当时 place 目标求出的放置解。

每组 14 个值的顺序是左臂 7 关节后接右臂 7 关节：

```text
L_shoulder_pitch, L_shoulder_roll, L_shoulder_yaw,
L_elbow_roll, L_elbow_yaw, L_wrist_pitch, L_wrist_roll,
R_shoulder_pitch, R_shoulder_roll, R_shoulder_yaw,
R_elbow_roll, R_elbow_yaw, R_wrist_pitch, R_wrist_roll
```

导航集成把前 4 组用于抓取（预抓取/抓取/抬起/收回）。收回位会把箱体坐标系对齐到
`base_link`（中心 `rx=ry=rz=0`），但不是把左右腕关节直接清零：程序保留箱体到双手的
相对夹持变换，再反算两只腕部目标，以便搬运时箱体保持水平、重心姿态稳定。第 5 组可用于检查 DetectBox 的
5×14 完整性或旧的同工位调试，但**不得跨越到 `put1` 后直接使用**：机器人导航和重新
下蹲后，`base_link`/TF 已改变。

## 6. 抓取与放置的实际顺序

### 6.1 抓取段：预抓取 → 抓取 → 抬起 → 收回

导航流程到达 `box1` 后依次执行：腰部后仰、准备拍照姿态、`photo` 下蹲、DetectBox、`grasp` 下蹲，
然后使用本次 DetectBox `ik_data` 的前 4 组：

1. **预抓取**：双臂移动到箱体两侧的安全接近位。观察双臂是否对称、手腕是否位于箱体
   外侧，整个路径是否避开桌边、箱内物和机身。
2. **抓取**：双手到配置的侧面接触目标。程序没有力/接触判定；只能由监护员确认箱体未被
   推翻、压桌或卡住。
3. **抬起**：在抓取位基础上沿箱体竖轴上抬，当前配置抬起 `0.05 m`。确认箱体确实离桌、
   没有滑移、双臂负载和机身姿态正常。
4. **收回**：抬起后把箱子朝身体收回，箱子近身面距躯干前表面 5cm（目标近身面 X≈0.19m，
   由主程序常量 `BODY_SURFACE_X=0.142` + `RETRACT_BODY_CLEARANCE=0.05` 计算，按当前
   box_model 箱体尺寸反推中心目标）。同时把收回箱体中心姿态设为 `rx=ry=rz=0`，保持箱体
   长轴沿 `base_link +X`、中心 Y 对准 0；程序保留双手相对箱体的夹持关系重新计算腕部目标，
   不是将腕关节直接归零。观察收回过程中箱体不撞机身/腿部，停止后确认间隙约 5cm，才允许
   回导航站立高度并经 `mid1` 前往 `put1`。

每个路点发送前会打印当前 14 关节、目标 14 关节和最大差值；HTTP 200 后，再以
`/mc/joint_states` 等待最大关节误差不超过 `0.08 rad`，单路点超时 `20 s`。

### 6.2 放置段：当前 place IK → 放置 → 回拍照位

到达 `put1` 后顺序固定为：

1. 请求 `place` 下蹲建议，先 home，再按绝对值下蹲，并等待 TF 到位；
2. 检测节点按当前 `base_link` 高度持续发布 place 左右手腕目标；
3. 调用 `/demo3/arm_ik/compute_place_ik`，强制基于当前 place 目标重新求解；
4. 服务做 FK 收敛检查，返回 `success/message/joint_positions`；客户端还会检查恰好 14 个
   有限关节值；
5. HTTP 发送这组当前 place IK，并等待真实关节到位；
6. 操作员确认箱体已经由台面稳定支撑后，才确认“返回拍照位置”；
7. 双臂回拍照位，再恢复 biped 导航站立高度。

这个流程不会使用 DetectBox `ik_data` 的旧第 5 组（place 解）。若 `compute_place_ik`
未就绪、30 秒超时、求解未收敛或返回数据无效，放置步骤必须失败并中止，不能退回旧
place 解。

## 7. Debug 每一步观察和必须中止的提示

导航集成 `--debug` 有高层确认，机械臂/下蹲内部还有第二层确认。只有明确输入 `y` 或
`yes` 才继续。推荐按下表观察：

| 步骤 | 应观察什么 | 必须中止的情况 |
| --- | --- | --- |
| 站立、SetMap、重定位 | 机器人稳定，地图为 `lqx3`，全局定位成功 | 技能非 `SUCCESS`、定位漂移、现场与地图不一致 |
| NavTo `box1` | 路线清空，到点距离和朝向正确 | 停位偏差、碰桌风险、二维码/定位异常 |
| 准备拍照位 | 3 路点运动包络安全，最终打印“已到达拍照位置” | 读不到 `/mc/joint_states`、HTTP 非 200、到位超时、异常抖动/碰撞趋势 |
| `photo` 下蹲 | 建议量、当前/目标/站立高度合理；先 home 后下蹲；TF 到位 | service 不可用，数值与桌高明显不符，home 或下蹲超时，腿部不稳 |
| DetectBox | 稳定计数趋向 10，漏检不持续；中心、尺寸、桌面 Z 合理；result 完整 | `success!=True`、action 状态失败、中心/尺寸明显错误、`ik_data` 空/错误/非 5×14 |

| 预抓取 | 目标与当前差值合理，双手在箱外安全接近 | “无法读取当前手臂关节”、差值异常跳变、目标几乎一致警告、任何干涉 |
| 抓取 | 双手同时接近侧面，箱体姿态稳定 | 单侧先撞箱、推箱、压桌、关节告警、到位超时 |
| 抬起 | 箱体离桌且不滑，负载和重心稳定 | 箱体未离桌、滑移/倾斜、手臂不同步、机器人姿态异常 |
| 回导航高度、负载导航 | 箱体中心姿态保持 `rx=ry=rz=0`，经 `mid1` 到 `put1`，箱体和手臂不碰桌/机身 | 上升空间不足、箱体不稳、导航失败或路线被占用 |
| `place` 下蹲 | 放置台空闲，home 后 TF 到目标高度 | 台面有物、桌高/停位不对、任何超时或机身碰桌风险 |
| 重算 place IK | 打印“已按当前放置高度重新计算 place IK”及成功消息 | service 未就绪、30 s 超时、IK 失败/异常、非 14 个有限值 |
| 放置 | 箱体在台面范围内，运动路径无干涉，关节到位 | 箱体碰桌边/压桌、目标不在台面、HTTP 非 200、到位超时 |
| 回拍照位 | **先确认箱体由台面稳定支撑**，再允许双臂撤回 | 箱体仍由手臂承载、会随手臂移动/跌落、回撤路径被挡 |
| 最终站立 | 双臂已与桌/箱分离，站立空间安全 | 箱体不稳、双臂未脱离、TF 到位超时 |

以下文本或现象一律按“中止”处理。当前客户端对到位超时直接返回失败；不要绕过工作流
手工执行后续步骤：

- `action server 未就绪`、`goal 被拒绝`、`等待 DetectBox action 结果超时`；
- `suggest_crouch service 未就绪/请求失败/请求超时`；
- `compute_place_ik service 未就绪/请求超时/失败/返回的关节数据无效`；
- `IK 不可到达`、`IK 求解失败`、`IK 求解异常`、NaN 或非有限值；
- `无法读取 /mc/joint_states`、`无法读取当前手臂关节`、TF 查询失败或使用固定高度回退；
- `等待……到位/完成超时，机器人可能仍在运动中`；
- `目标与当前关节几乎一致，机器人可能不运动（IK 可能未收敛）`；
- HTTP health 失败、HTTP 非 200、机器人控制器告警，或任何肉眼可见的意外运动、干涉、
  箱体滑移和人员进入运动区。

HTTP 200 只表示服务接收命令，不表示动作完成；没有对应“已到达/已完成/到位”日志就不能
确认下一步。

## 9. 故障排查

| 现象 | 检查与处理 |
| --- | --- |
| 点云无数据或类型错误 | 检查相机进程和 `/sensor/camera/stereo/pointcloud/raw`；不要改成 README 中历史话题名后盲试。 |
| 持续 `box_not_found`、稳定计数不升 | 清除遮挡，核对 `small_box3`、桌高、工作空间 `[-0.20,-0.80,-0.10]～[1.00,0.80,0.50]`、点云 frame/TF；不要移动箱子凑稳定计数。 |
| 桌面高度校验失败 | 抓取/放置桌必须在 `0.75–1.10 m`，且配置与系统实测一致；停止并重新标定，不能绕过校验。 |
| 检测尺寸或中心明显错误 | 检查箱型、桌面平面、相机标定、TF 和点云偏移；删除错误结果，不执行 IK。 |
| action 未就绪/goal 被拒 | 保持 `run.sh` 运行，检查 `/demo3/box_grasp_demo/detect_box`；已有 goal 时等待其明确结束或取消后再试。 |
| `ik_data` 为空或含 error | 查看 IK 节点的目标缺失、TF 和收敛日志；不得复用上一轮结果。 |
| `suggest_crouch` 不可用或数值异常 | 检查 `/demo3/box_grasp_demo/suggest_crouch`、桌高配置和 `base_footprint → base_link`；修复后从安全初始状态重跑。 |
| `compute_place_ik` 不存在 | 新接口未构建或 IK 节点未重启；重新 `colcon build`、source 并重启 `run.sh`，确认 `/demo3/arm_ik/compute_place_ik`。 |
| 当前 place IK 不收敛 | 核对已到 `put1` 且 `place` 下蹲到位，检查 `place_x/y/yaw`、桌高、动态 TF 和 IK 日志；不要改用检测时旧第 5 组。 |
| HTTP health/动作请求失败 | 检查 `MOTION_BASE_URL`、网络、代理进程和 API key；未确定上一命令是否被接收前不要重复发送。 |
| HTTP 200 后未到位 | 读取 `/mc/joint_states`、TF、目标差和控制器告警；中止后续步骤，确认机器人是否仍在运动。 |
| 箱体在抓取/抬起后不稳 | 不开始导航或上升；清空周围并按现场批准的硬停和人工恢复方案处理，重新放稳后从头验收。 |
| 放置后箱体仍随手臂运动 | 不确认“返回拍照位置”；说明箱体尚未由台面支撑，使用现场批准的恢复方式，不能依赖程序自行纠正。 |

## 10. 失败恢复与 Ctrl+C 边界

1. **命令尚未发送时**：在 debug 提示回答 `n`，流程会失败即停；修复配置、接口、现场或
   定位问题后，从已确认的安全初始状态重新开始，不跳过中间步骤。
2. **DetectBox 正在执行时**：导航工作流退出清理会尝试取消活动 goal；这只停止感知/IK
   action，不是机器人机械动作停止手段。
3. **HTTP 已返回 200 或可能已经被接收时**：不要重复发送，也不要假定关闭终端会停机。
   保持运动区隔离，观察 `/mc/joint_states`、TF 和控制器状态；存在危险时立即使用现场已
   验证的硬停/急停。
4. **抓取途中失败**：不恢复导航、不继续下一个 IK 点。先判断箱体是否仍由桌面支撑、是否
   被夹持或悬空，再由有权限人员按现场恢复方案卸载和复位。
5. **负载导航途中失败**：`Ctrl+C` 会请求停止当前 UBT Work，但不证明箱体稳定。确认机器人
   和箱体静止、路线隔离后再人工处置，不直接续跑剩余步骤。
6. **放置途中失败**：箱体未明确受台面支撑前，不发送回拍照位；已经支撑后也要先确认双臂
   可安全撤离，再按 debug 流程恢复。

> **必须牢记：已经发给 HTTP 服务的机械臂或 biped 命令不能由 `Ctrl+C` 撤回。** 当前代码
> 没有 HTTP cancel/stop。`Ctrl+C` 只能中止本地编排，并在导航技能进行时请求停止当前 UBT
> Work；机器人端已接收的 HTTP 动作仍可能继续执行。危险情况下以现场验证过的硬停/急停
> 为准。
